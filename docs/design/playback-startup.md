# 起播延迟：从点下播放到画面动起来

> 状态：**iOS App、服务端、网页播放器均已实施；iOS 真机与网页（无头 Chrome）连 NAS 验证（2026-09-27）**。
> 前置阅读：[web-player.md](web-player.md) §6.10（起播链路）、[ios-app.md](ios-app.md) §4（多引擎）、
> [player-pipeline-optimization.md](player-pipeline-optimization.md)。本文只记这一轮「秒开」优化的
> 测量手段、找到的问题、改法与实测数字，不重复那几份文档已经写过的东西。
> 2026-09-28 起 App 已移除 MPV，原文件直出由自研引擎完成（[player-engine.md](player-engine.md)）；下文与 MPV 相关的条目只作历史记录。

## 0. 目标与口径

用户的要求：点了播放就立即播放，体感对齐 Infuse。口径统一为**从点下播放键算起**：

- **首帧**：第一帧画面可以上屏（AVPlayer 的 `isReadyForDisplay`；自研引擎报首帧）；
- **播放**：画面开始动（引擎报 playing）。

以前只有一个 ttff（从控制器发请求算到 playing），不含播放器弹出与音频会话，也看不出慢在哪一段。

## 1. 测量手段（保留在代码里，以后排查直接用）

- **起播分段计时**（`apps/apple/.../PlaybackStartupTrace.swift`）：出现 → 算好请求 → 开始请求 → 决策 →
  会话 → 建引擎 → 引擎 → 就绪 → 定位 → 首帧 → 播放，每段距点击的毫秒数。首帧一出上报一次
  `client-log` 的 `startup` 事件，服务端记成 INFO 一行「起播分段：…」（NAS 按天日志可查），
  开发期同时打控制台 `[StartupTrace]`。**用户说「这部片起播慢」时先看这一行。**
- 开发期的辅助（仅 Debug 包）：`[AVStartup]` 打印 AVPlayer 自己的起播明细
  （`AVMetricPlayerItemInitialLikelyToKeepUpEvent`，每个列表 / 分片请求的起止）；`[FrameStats]`
  每 5 秒一行帧统计（`-mcFrameStatsEverySecond YES` 改每秒）；`-mcRouteDelay <秒>` 让 `-mcRoute` 等落地页冷启动请求跑完再开（排除连接池拥挤）；
  `-mcAutoHoldSpeed <秒>` 到点自动长按 2 倍速 15 秒。
- 服务端既有：「播放会话就绪：档 · 决策 · 准备 · ffmpeg · 共」「首片供给…距会话创建」「分片就绪…等待」。
- 片库级统计：`playback_metric` 表的 ttff 按引擎 × 档位分组（本轮起点：AVPlayer 档 0 中位 4.6 秒、p90 10 秒）。

## 2. 找到的问题与改法

按对起播时间的影响从大到小。数字是模拟器连 NAS / iPhone Air 真机实测。

| # | 问题 | 改法 | 位置 |
|---|---|---|---|
| 1 | 续播走 HLS 时 AVPlayer 先要第 0 段，把正从续播点起转的转码拉回片头重启一轮、seek 过来再重启一轮（远程转码续播首片 10 秒） | VOD 列表写 `EXT-X-START`（起播点夹进服务端起转那一段内部，离两端各 2 毫秒，防 EXTINF 累加误差把边界上的起播点算进前一段）；就绪时已在起播点就不再零容差 seek | `hls_vod.py`、`session.py` `playlist_start_ms`、`AVPlayerEngine` |
| 2 | 服务端在「落后转码头的请求」上先熬 3 秒宽限期（为防 AVPlayer 的杂散第 0 段请求），边界起播点被算进前一段时白等 3.2 秒 | 同上，起播点不再落进前一段 | 同上 |
| 3 | MPV 放原文件前，服务端仍按 MPV 能力开一路换封装会话（冷启动先采样关键帧 1.6 秒、拉起 ffmpeg），客户端随即丢掉 | MPV 打算直出时申报 `universal`（全解码播放器）：服务端直接给档 0 原文件地址，不采样、不起 ffmpeg；多剪辑原盘照样给不转码的 HLS。全解码分支补上字幕清单与用户选的音轨 | `schemas/playback.py`、`decide.py`、`PlayerCapability.mpv(original:)` |
| 4 | 决策与开会话的每一步都回主线程续跑（工程默认 MainActor + 平易并发，nonisolated 异步函数跟随调用方），播放器弹出时主线程忙着转场，起播请求排队 110~250 毫秒 | 请求内容在主线程一次算好，`PlaybackAPI.negotiate`（`@concurrent`）在后台一口气跑完「决策 → 选引擎 → 开会话」 | `PlaybackAPI.swift`、`PlaybackController.request` |
| 5 | 起播期间关掉了「预计不会卡」的等待前，AVPlayer 首帧出来后还要干等 300~600 毫秒攒缓冲才动 | 挂上就 `playImmediately`，起播时 `automaticallyWaitsToMinimizeStalling = false`，第一次 playing 后再打开（只开一次，重复设置会让它在等待 / 播放间来回跳） | `AVPlayerEngine.load` |
| 6 | 首次决策现场用 ffprobe 从网络挂载上采样三段各 30 秒码流（0.4~1.4 秒） | Matroska 先用容器自带的 Cues 算平均关键帧间隔（开会话本来就要读、结果缓存）；索引缺失、覆盖不全或比门槛稀时才采样核实 | `media_probe._cues_keyframe_interval` |
| 7 | 页面请求（发现页一次二十来个 TMDB 列表）占满连接池，起播请求在本机排队（冷启动直达播放页实测排队 8 秒） | 播放专用 `APIClient.playbackSession` | `APIClient.swift` |
| 8 | 能力快照里 `VTIsHardwareDecodeSupported` 首次调用 60 毫秒，正压在请求发出前 | 进程内缓存，App 启动时后台预热 | `PlayerCapability.prewarm` |
| 9 | 开会话查配额时 `rglob` 整个转码缓存两遍（NAS 两千多个分片，每遍 50 毫秒，同步卡在事件循环上） | scandir 逐层走、每个文件只 stat 一次，只在真淘汰过后重算（15 毫秒） | `session.usage_bytes` |
| 10 | 系统播放器建引擎要等主线程，拿到地址到开始读文件头之间空转 70~90 毫秒 | 后台协商一拿到地址就建 `AVURLAsset` 并开始加载，挂引擎时接上（A/B 中位数快 100 毫秒） | `negotiate` 末尾、`AVPlayerEngine.prepare` |
| 11 | `init.mp4` 放行前一律隔 50 毫秒采样两次大小 | 已有产出分片的会话、远程原子落盘的产物，非空即放行 | `routes/playback.py` |
| 12 | 激活音频会话、锁屏信息注册排在发请求之前 | 音频会话放后台；先发请求再做杂事 | `PlaybackController.start` |

### 流畅度（起播后被切成转码 = 最糟的「慢」）

| # | 问题 | 改法 |
|---|---|---|
| 13 | 长按 2 倍速时 mpv 按音频节奏丢帧（4K 60 帧就是每秒 120 帧），掉帧看门狗 3 秒就判「直通放不动」换成转码 | 倍速期间不判掉帧；回到原速后 8 秒追赶宽限期（真机 4K 60 帧约 6 秒追平） |
| 14 | mpv 默认画质档在手机上放 4K 60 帧 HDR 横屏贴着 GPU 上限，发热后成段掉帧回落（真机交替对比：默认档 3/3 回落，fast 档 60 秒掉 2~26 帧） | mpv 默认 `profile=fast`（双线性缩放、不抖动、不逐帧测 HDR 峰值），`framedrop=decoder+vo`（落后时解码端也跳帧，追平从 >8 秒缩到 6 秒） |
| 15 | MPV 直出的掉帧门槛与网页同为 10%，60 帧片子掉 10% 还剩 54 帧，回落却要中断重开、降到 1080p，远程转码 4K 60 帧还不一定供得上 | MPV 门槛 25%（真放不动时掉帧在 50% 以上），系统播放器仍 10% |
| 16 | AVPlayer 引擎状态抖动时，控制器每收到一次 playing 就补发一条进度（起播 20 秒 160 多条） | 只在从暂停恢复时补报 |

## 3. 实测结果

iPhone Air 真机连 NAS（Wi-Fi），点击 → 首帧：

| 路径 | 改前 | 改后 |
|---|---|---|
| 系统播放器 · HLS 换封装（档 1） | 中位 0.87 秒 | 0.31~0.62 秒（续播 0.51 秒） |
| 系统播放器 · 转音频（档 2） | 中位 1.7 秒 | 0.45~0.57 秒 |
| MPV · 4K HDR / 杜比视界原文件 | 0.5~0.9 秒 + 冷启动 1.8 秒会话（常被掉帧回落打断） | 0.46~0.58 秒，发热状态横屏 60 秒掉 2~5 帧 |
| 系统播放器 · MP4 直出（档 0） | 中位 4.6 秒（片库统计） | 0.7~0.8 秒（0.12 秒即开始播放） |
| 远程转码（Mac mini）续播 | ~10 秒 | 0.4 秒（有缓存）/ 1.6 秒 |

MP4 直出剩下的大头是 AVFoundation 解析长片 moov（1 小时 43 分钟的采样表，本机 0.4~0.6 秒，与 moov
在头在尾无关——对照实验见提交记录），客户端压不下去。

## 4. 已知未解

- ~~**后台任务与起播抢解释器**~~（已解决）：站点种子同步收尾的「发布时间预测重算」每轮把几万行种子索引读进
  Python 逐行解析，虽在线程里跑，仍与事件循环抢 GIL——真机实测撞上时条目 / 决策 / 开会话从几十毫秒涨到
  1.2~2.5 秒。根因是白算（一整天的重算一次都没改变结论），改为 SQL 预筛 + 按变化触发后工作量只与在追剧的
  相关种子成正比，见 subscription-release-forecast.md §7。
- 服务端 VOD 会话的 0.3 秒快速失败窗口：首片生产本身多在 0.4 秒以上，窗口与之重叠，暂不动。

## 5. 网页播放器

网页的主链路此前已经优化过（web-player.md §6.10：播放页地址算出播放单元、立即挂播放器、续播点并进
开会话、hls.js 与会话并行热身、条目页预取路由），无头 Chrome 连 NAS 实测点击 → 开始播放：档 1 HLS
0.2~0.35 秒、档 2 转音频 0.29 秒、档 0 MP4 直出 0.4 秒（热）。这一轮补的是剩下的余量与测量：

| # | 问题 | 改法 |
|---|---|---|
| W1 | 条目页只预取电影形态的 `/play/{id}`，剧集 `/play/{id}/sXXeYY` 不命中，点播放要现取一次 RSC 载荷、期间条目页原地卡着 | 预取播放键实际要去的地址（跟随选中的集）；条目加载后顺手热身 hls.js 分包与解码能力快照（首次要问浏览器 34 次） |
| W2 | 会话一落地就挂字幕：内封轨第一次要服务端整文件抽取、与首片抢盘，VTT 还被自绘层与画中画补丁轨各拉一遍 | 字幕等这一集第一次 `playing` 之后再挂（晚零点几秒出字幕，换首帧早出来） |
| W3 | 首帧指标：开播后重开会话（换轨 / 画质 / 带宽重开）会覆盖起点，首帧早于起点被夹成 0 上报；起播前的 `waiting` 被记成一次卡顿；退出时上报的引擎是空串 | 起点只记每集第一次；起播请求后、首帧前的等待不算卡顿；挂引擎时记下引擎名 |
| W4 | 没有分段计时 | 与 App 同口径的 `startup` 上报（`lib/player/startup-trace.ts`），起点取条目页点播放的时刻（`markPlayIntent`）；服务端同样记成「起播分段」 |
| W5 | 原生 HLS（无 MSE 的老 iOS Safari）在 loadedmetadata 无条件 JS seek，压在分片边界的续播点会去要前一段 | 已在起播点（EXT-X-START 生效）就不再跳 |
| W6 | `hls-back-buffer`（按码率调回看缓冲）起播时一连好几条、按 WARNING 记 | 服务端按 INFO 记 |
| W7 | （2026-10-01）网页第一次播需要换封装的 MP4（音轨 AC3 / DTS 等浏览器不支持）：开会话「准备」要等全片关键帧索引，MP4 用 ffprobe 列包会读出每个包的数据，NAS 的 NFS 片库上一部 10 GB 的片子 93 秒；决策阶段的三段关键帧采样另要 2.2 秒 | MP4 / MOV 读 moov 样本表算关键帧呈现时间、32 路并发抽检至多 128 个关键帧样本的 NAL 类型，对不上交还 ffprobe；起播后后台全量核对（web-player.md §14.3）。同一部片冷缓存首播：开会话 96 秒 → 0.63 秒。要 ffprobe 通读才有索引的（TS 等）开会话不再当场通读，先走会话相对模式、后台补索引：36 GB 的 TS 冷缓存首帧 126 秒 → 5.1 秒 |
| W8 | 详情页起播预热只替「上报过解码能力的客户端」采样关键帧，而能力只在 `/decide` 里记；网页早已改成直接开会话（W1 之前的 §6.10 改造），预热对网页从未生效 | 开会话也记下浏览器的解码能力（App 不记）。NAS 实测：先开详情页再起播，冷缓存 TS 的决策 3.0 秒 → 17 毫秒、首帧 1.9 秒 |

**已知未改（有意保留）：** Safari 手势只在点击后约 1 秒内有效、且不跨网络回调，从条目页点进来可能要再点
一次播放。静音起播兜底被明确否决过（`lib/player/autoplay.ts` 的注释：用户会以为片子没音轨），根治要在
点击那一刻解锁 `<video>` 元素并交给播放器复用，改动面大，需在真 Safari 上验证后再做。
