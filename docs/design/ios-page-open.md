# 媒体库 / 订阅首页秒开：从点下页签到整页出齐

> 状态：**iOS App 已实施；模拟器连本地实验室（真实后端 + 大体量数据 + 链路模拟）与家里 NAS（真实数据）验证（2026-09-27）**，
> 真机待验收。前置阅读：[ios-app.md](ios-app.md) §3.2（页面骨架）。本文只记这一轮「秒开」的
> 口径、测量手段、找到的问题、改法与实测数字。

## 0. 目标与口径

用户的要求：打开媒体库和订阅页面时获得极致的加载速度。先定「快」指什么——**接口快不等于页面快**：
基线里服务端单个接口多在 5～150ms，页面却要 1～2 秒才出齐，时间花在串行等待、本机排队、主线程与图片上。

口径统一为用户感受到的「打开完了」，起点是用户的动作：

| 指标 | 起点 → 终点 | 业界对应 |
|---|---|---|
| 首帧（TTID） | 冷启动从 main、切页签从选中那一刻 → 页面第一次随 Core Animation 事务提交上屏 | Apple 首帧 400ms 内（WWDC19 Optimizing App Launch）、Android TTID |
| 数据就绪 | → 页面数据全部渲染上屏（不再有转圈、骨架、分批插进来的行） | — |
| **视觉完成（TTFD，主指标）** | → 数据就绪，且首屏里每张图都已显示、不再渐显 | Android TTFD、Web LCP（≤2.5s 为好，按 P75）、国内 APM「页面秒开率」 |
| 卡顿 | 主线程连续占用 | Apple：≥250ms 为 micro-hang、≥500ms 为 hang；帧预算 16.7ms / 8.3ms |
| 版面稳定 | 首帧之后页面是否再「长」出东西 | Web CLS ≤0.1 |

人因参照：0.1 秒内感觉是瞬时，1 秒内不打断思路（Nielsen）。本轮目标：**切页签视觉完成 ≤200ms，
冷启动落在媒体库 / 订阅首页时第一帧就是完整页面；从未打开过（没有本机数据）的也在 1 秒内**。

## 1. 测量手段（保留在代码里，以后排查直接用）

- **打点**（`Core/PerfTrace.swift`，仅 Debug 包、`-mcPerf YES` 启动才记）：每次页面打开记首帧 / 数据就绪 /
  视觉完成 / 分几拨到达；每个接口的本机排队、TTFB、下载、解码耗时与是否在主线程解码；每张首屏图来自
  内存 / 磁盘 / 网络。事件写 App 容器的 jsonl，同时打 os_log 与 Instruments 的 Points of Interest
  （Time Profiler 里和 CPU 采样对得上）。
- **自动化**（`scripts/perf/ios_open_bench.py`）：编译 Debug 配置 + `-O` 的包（真实优化级别、调试参数可用），
  反复冷启动，按剧本切页签（`-mcTab` 冷启动落点、`-mcPerfScript "library@4,subscriptions@8"` 按时刻切），
  收回打点汇总中位数 / P90；`timeline` 看单轮时间线。A/B 交替装包跑，抵消机器负载漂移。
- **实验室**（`scripts/perf/ios_lab.sh`）：真实后端 + 按重度家庭用户生成的数据（12 个库约 1 万条目、
  20 行首页、150 部收藏、300 部订阅）+ 离线假图床（真实尺寸与体积的海报 / 4K 背景 / 透明 Logo）+
  链路模拟（lan：RTT 6ms、200 Mbps；wan：RTT 70ms、25 Mbps，带宽全连接共享）。
- **录屏逐帧核对**：`simctl io recordVideo` + 帧差，确认打点的「首帧」就是屏幕上内容出现的那一帧、
  之后画面是否还在变（发现了图片渐显这一段）。

模拟器的两个偏差，读数字时要记住：main 之前的 dyld 加载要 1.5～3 秒，几乎都是模拟器运行时自己的系统库
（真机在共享缓存里），所以冷启动从 main 算；Swift 协议一致性查找在模拟器上没有预计算（真机 iOS 16 起
在 dyld 闭包里算好），「第一次上屏」的主线程时间模拟器上偏高（Instruments 里占三到四成）。

## 2. 找到的问题与改法

按对打开时间的影响从大到小。

| # | 问题 | 改法 | 位置 |
|---|---|---|---|
| 1 | 什么都不存本机：冷启动、第一次切过去都从转圈开始等网络 | **页面快照**：三份数据加载成功即按「服务器 + 账号」存 Library/Caches，下次先原样画出、再静默刷新；退出 / 移除账号即删 | `PageSnapshots`、`LibraryHomeStore`、`SubscriptionIndex`、`SubscriptionsHomeFeed` |
| 2 | 冷启动先等「测服务器 + 问身份」两个来回才出主界面，期间一个转圈 | **会话快照**直接进主界面，身份在第一帧之后后台校验，401 照常回登录页 | `SessionCache`、`AppModel.init/revalidate` |
| 3 | 媒体库首页「偏好 → 库与合集 → 接下来继续与收藏 → 各行」四跳串行，最后一跳 17 个请求受每主机 4 连接限制排队（最长 300ms+），且要等最慢的一行 | 行清单已知时五个请求同发，各行在库与合集一到就发（两跳）；有快照后不再在关键路径上 | `LibraryHomeStore.load` |
| 4 | 订阅首页先等整份清单（274KB，服务端 127ms，并发时 500～1000ms）再发预告 / 刚刚入库 / 下载快照 | 已知有订阅时四个请求同发；进页面那次不再和轮询重复取下载快照 | `SubscriptionsView.reload` |
| 5 | Hero 先按「只有清单」挑兜底的「追踪中」剧照，预告到了再整个换成另一部（换片 + 重下 1～2MB 原图） | 快照里三份数据同时在，第一帧就是最终的 Hero | 同 #1 |
| 6 | 接口响应在主线程解码（工程开着易上手并发，非隔离 async 函数跟随调用方），每次打开主线程上 25～55ms | `APIClient.send/raw/upload` 标 `@concurrent`，请求与解码一律在后台 | `APIClient` |
| 7 | 页面出来后图片还要从磁盘读、解码，再渐显 0.2 秒——录屏看，页面出现后又过 144～220ms 才稳定 | **首屏图片预热**：按页面排版算出第一屏的图，提前解码进内存（命中内存时 LazyImage 当场出图、不渐显） | `FirstScreenImages`、`*.firstScreenImageURLs` |
| 8 | 页面在这次运行里第一次上屏特别重（模拟器约 300ms，第二次约 60ms） | **页面预热**：落地页空闲后在背后不可见地把两个页签各画一遍（不发请求、不轮询），同时刷新数据、预热图片 | `MainTabView` 的 `PageWarmup` |
| 9 | 冷启动直接搭主界面后，发现页取数与几十张图的完成回调把主线程连续占满，第一帧推迟到约 1.7 秒 | **首帧闸门**：发现页取数、角标轮询、头像绘制、身份校验、其它页签的图片预热等第一帧上屏再做 | `FirstFrameGate` |
| 10 | 路由表 `some View` 是三十来个页面套成的巨型泛型，每个导航栈第一次建起来都要把全部页面的类型实例化一遍 | 类型擦除成 `AnyView`，各页面只在真正打开时实例化 | `Destinations.swift` |
| 11 | 身份校验每次都给 `phase` 重新赋值，整个主界面按「会话变了」重算 | 会话完全一样时不动 | `AppModel.update(session:)` |
| 12 | 标签栏图标按 200pt 画、逐像素找外框，冷启动首帧前五个合计约 40ms | 按 64pt 画 | `TabIcon` |
| 13 | 订阅首页整页排版对同一批时间串反复解析（一次几百次） | 解析结果缓存 | `Formatters.date` |

## 3. 实测结果

模拟器（iPhone 18 Pro，M1 Mac mini）连实验室，Debug 配置 + `-O`，原版（同一份打点）与优化版交替装包，
各 6 轮（冷缓存 3 轮），中位数（P90），单位 ms：

LAN（RTT 6ms）：

| 场景 | 原版 | 优化后 |
|---|---|---|
| 第一次切到媒体库 → 视觉完成 | 823（831） | **201（236）** |
| 第一次切到订阅 → 视觉完成 | 1107（1381） | **166（173）** |
| 再次切换（媒体库 / 订阅） | 64 / 77 | 51 / 60 |
| 冷启动落在媒体库 → 视觉完成（从 main） | 1672（2090） | **831（945）**，首帧即完整 |
| 冷启动落在订阅 → 视觉完成（从 main） | 1855（1957） | **974（992）**，首帧即完整 |
| 刚安装 / 缓存被清：第一次切到媒体库 | 878 | **453** |
| 刚安装 / 缓存被清：第一次切到订阅 | 1090 | **223** |
| 管理员冷启动落在发现页：首帧 / 视觉完成 | 1722 / 1780 | **1046** / 1631 |

WAN（RTT 70ms、25 Mbps，模拟在外用蜂窝网连家里）：

| 场景 | 原版 | 优化后 |
|---|---|---|
| 第一次切到媒体库 → 视觉完成 | 1189（1325） | **188（192）** |
| 第一次切到订阅 → 视觉完成 | 1297（2534） | **162（172）** |
| 冷启动落在媒体库 → 视觉完成（从 main） | 2076（2109） | **868（913）** |
| 冷启动落在订阅 → 视觉完成（从 main） | 2443（2610） | **909（1082）** |
| 管理员冷启动落在发现页：首帧 / 视觉完成 | 1446 / 2059 | **1039** / 1780 |

优化后 WAN 与 LAN 几乎一样：网络已不在打开的关键路径上，只决定「多久换成最新数据」；原版随链路变差明显变慢。

NAS（家里 NAS 真实数据：2 个库、622 部电影 / 262 部剧集；有线局域网），同样交替各 6 轮：

| 场景 | 原版 | 优化后 |
|---|---|---|
| 第一次切到媒体库 → 数据就绪 | 775（954），图片还要更晚 | **202（276）**，首帧即完整 |
| 第一次切到订阅 → 视觉完成 | 598（776） | **132（169）** |
| 冷启动落在媒体库 → 数据就绪（从 main） | 2281（3182） | **901（1225）**，首帧即完整 |
| 冷启动落在订阅 → 视觉完成（从 main） | 2066（2235） | **976（1156）** |
| 管理员冷启动落在发现页：首帧 / 视觉完成 | 1630 / 1774 | **1096** / 1705 |

NAS 上服务端明显比实验室慢（TTFB 中位 / P90，ms）：`/playback/stats/watch` 864 / 1304、`/subscriptions`
345 / 758（只有 6KB）、`/downloaders/tasks` 314 / 622、`/playback/up-next` 296 / 1127、
`/libraries/{id}/items` 235 / 809，冷启动并发时单个能到 1.2～1.4 秒。优化后页面不再等它们，但它们决定
「多久换成最新」，值得在服务端单独查（见 §5）。

录屏核对：优化后第一次切过去，内容出现的那一帧之后画面不再变化；只做快照、还没做图片预热时，内容出现后
还要 144～220ms 的图片渐显才稳定。

## 4. 行为变化与取舍

- **冷启动连不上服务器**：不再停在欢迎页的「连不上」卡片，而是进主界面显示上次的数据，各页挂自己的
  「与后端通信失败」提示；令牌失效（401）照常回登录页。改地址 / 换账号从「我的」页的账号切换进。
- **页面第一帧是上次离开时的数据**，随后刷新；通常在切过去之前已被空闲预取刷新好，切过去后不再换一遍。
  整周预告按天算，隔天的快照不用它（Hero 与日程等网络的新数据）。
- **预热的代价**：启动约 2 秒后，主线程各有一块约 140ms（模拟器）用来预画两个页签；首屏图片多占内存
  （订阅 Hero 的 4K 原图解码后约 33MB）。
- 快照放 Library/Caches（系统可清，清了只是退回走网络），按账号隔离，退出 / 移除账号即删。

## 5. 未解与下一步

- 管理员的落地页（发现页）本身首帧重：模拟器约 1 秒才上屏、1.6 秒出齐；同样的快照做法可以让它首帧即完整。
- 服务端三个订阅接口（清单、整周预告、刚刚入库）各自现算整份订阅清单（逐条查条目），NAS 上 CPU 更弱会
  更慢；现在不在页面打开的关键路径上，但仍决定「多久换成最新」与冷启动时的服务端争抢。
- NAS 上服务端接口普遍慢（§3 末尾的表），订阅清单 6KB 也要 0.35～1.4 秒，疑与同步任务抢 GIL 有关
  （[playback-startup.md](playback-startup.md) 未解项同源），需服务端单独排查。
- 真机验收：模拟器的「第一次上屏」主线程时间偏高，真机数字应更好，待实测。
